# M2 — the Library: books, chapters, a shared universe, and everything in and out

Written 2026-09-20, after M1's UI rebuild landed (all 38 tasks of
`docs/specs/2026-09-19-ui-redesign.md`). This plan fully specifies M2 and is the source of truth
for it; its Progress list is what the loop reads.

M2 is the milestone that turns a pile of chats into a library you can live in: stories gather into
**books**, a long story reads back as **chapters**, the same person can walk between stories, and
what other apps made can come in — and everything you have can go out again.

## 1. What M2 is, from the master spec

> Library: Book → Story → Chapter (a chapter **is** a message range — one hierarchy, not two);
> folders as a view, tags as the organiser; shared-universe entities with per-story overrides
> (`origin_entity_id`); `story_links` (continuation / shared universe / reference) feeding
> retrieval with a story-time offset; import Character Card V2/V3 PNG (`ccv3` / `chara` tEXt
> chunks), ST World Info → `pinned` / tagged memories, ST chat JSONL; `.kataki` zip export
> (db + blobs) + Markdown/JSONL story export

Everything below is that, made concrete.

## 2. The decisions this plan makes

1. **One hierarchy.** A book holds stories in an order. A chapter is a *range of messages inside
   one story*, not a container: `chapters(story_id, title, from_message_id, to_message_id?)`. An
   open chapter has no end and runs to the newest line. Nothing about the message tree changes.
2. **Folders are a view, tags are the organiser.** No folder table. A folder is a saved filter
   over tags (`{name, kind, tags[]}` in settings), and the UI shows it like a folder. Stories get
   tags of their own, the way library items already have them.
3. **The same person in another story.** Two story entities are the same person when they came
   from the same library item, or when one's `origin_entity_id` points at the other. A character
   the reader invented in one story can be adopted into the library and then be the same person
   everywhere. Per-story overrides stay where they are: the entity row already snapshots the
   description and carries its own flags and memories.
4. **A link is a promise about time, not a leak.** `story_links(from_story_id, to_story_id, kind,
   offset_min, note)` where kind is `continuation | shared_universe | reference`. Memory crosses a
   link only for a character who is in both stories, only in the direction of the link, and only
   with the offset applied to story time, so six years in one story is six years in the other. A
   character never recalls something their other self only witnessed in a story they were not in.
5. **Imports never overwrite.** Everything imported lands as new rows; a name clash makes a second
   item, never a silent merge. The importer reports what it made and what it skipped.
6. **Exports are plain.** `.kataki` is a zip: `library.db`, `blobs/`, and a `kataki.json` manifest
   with the schema version. A story exports as Markdown (readable) or JSONL (one line per
   message), both without the engine's private bookkeeping.
7. **No new dependencies.** PNG chunks are `struct` + `zlib`, CHARX and `.kataki` are `zipfile`,
   everything else is `json`. All stdlib.

## 3. The engine

### 3.1 Schema (migration 7)

```sql
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  blurb TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP);

ALTER TABLE stories ADD COLUMN book_id INTEGER REFERENCES books ON DELETE SET NULL;
ALTER TABLE stories ADD COLUMN book_order INTEGER NOT NULL DEFAULT 0;

CREATE TABLE chapters(                      -- a range of the story's own messages
  id INTEGER PRIMARY KEY,
  story_id INTEGER NOT NULL REFERENCES stories ON DELETE CASCADE,
  title TEXT NOT NULL,
  from_message_id INTEGER NOT NULL,
  to_message_id INTEGER,                    -- NULL: still being written
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP);

CREATE TABLE story_links(
  id INTEGER PRIMARY KEY,
  from_story_id INTEGER NOT NULL REFERENCES stories ON DELETE CASCADE,
  to_story_id INTEGER NOT NULL REFERENCES stories ON DELETE CASCADE,
  kind TEXT NOT NULL CHECK(kind IN('continuation','shared_universe','reference')),
  offset_min INTEGER NOT NULL DEFAULT 0,    -- add to the other story's story_time
  note TEXT,
  UNIQUE(from_story_id, to_story_id, kind));
```

`entities.origin_entity_id` already exists (M1 left it as the seam); M2 gives it an index and a
meaning.

Story tags reuse the existing `taggings(obj, obj_id, tag_id)` table with `obj='story'`.

### 3.3 What a link does to memory (task 6)

`retrieve.recall` gains linked stories: for the knower, find their other selves (same
`lib_item_id`, or joined by `origin_entity_id`) in stories linked *from* this one. Their memories
join the candidate set with:

- the other self asked as of `their last line + offset_min + our own clock`, so the offset reads as how long after that story this one begins and decay runs on one timeline,
- a source penalty of one step (what you remember from another life is hazier),
- the same hard gate as always: only what *that* self actually knew.

A `reference` link carries no memory at all — it is a note for the reader, and only the story's
own pinned facts cross. `continuation` and `shared_universe` carry memory; only `continuation`
carries the clock forward by default (`offset_min` set from the two stories' own times).

## 6. Loop protocol

As M1's, unchanged: one task per iteration, test-first in the engine, the design's classes in the
app, tick the box and add a note line in the same commit, `git add <paths>` only, never push, stop
every background process the iteration started, and report in three lines.

Adversarial review before each commit, as in M1: reviewers by dimension, then a skeptic per top
finding, and only fixes that survive.

## 7. Risks

| Risk | Containment |
|---|---|
| Cross-story recall leaks what a character never knew | The hard gate stays per entity: only that self's knowledge rows, only through a link, only in its direction. Tests for both directions and for an unlinked story. |
| An import corrupts a good library | Imports run in one transaction and report what they made; `.kataki` import refuses a non-empty library unless asked. |
| Card formats in the wild are messy | The importer takes V2, V3, CHARX and bare JSON, and never rejects a card for an unknown field. Fixtures for each shape. |
| M2's UI drifts from M1's | Same classes, same spacing, and every screen shot beside an M1 screen before it is committed. |
